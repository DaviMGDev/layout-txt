## Active decisions (all locked from the convergence round)
- LAYOUT.txt format v1 as per the exported proposal (discussions/layout-spec-format/layout-txt-format.md): label-first [Label](type:variant attrs), (type) containers, xN repetition, # notes, text lines, per-screen files, structural verifier, free-form vocabulary with unknown types = INFO only.

## Open questions (current turn)
- Catalog rigidity: should there be a builtin/recommended component catalog, or fully loose usage? (design tension — answering this turn with a three-tier model: rigid grammar, loose vocabulary, non-normative recommended core; options A minimal-universal-core vs B no-core at all vs C rich catalog ~25+)
- Related: where the recommended vocabulary lives (format spec doc section, verifier typo-whisper INFO) and whether it's global vs per-project.

## Reasoning chains
- InterSpec's CATALOG.md is normative (rigid, must-know builtins, new components need language-level definitions) — that rigidity was part of the felt weight; a growing catalog is the bloat the format exists to escape.
- DESIGN.md precedent: "Recommended Token Names (Non-Normative)" — guidance without validation; the same pattern applies to LAYOUT widget types.
- The format owns shapes, not vocabulary (thinker soft spot #1, accepted). Catalog-as-convention stabilizes agent mappings and enables typo-suggestion INFO ("buton" → button?) without enforcement.
- Exotic widgets work via passthrough attrs: [Revenue](graph data=monthly) — type graph, attrs opaque. No language change needed.

## Key insights
- Boundary rule: grammar closed, vocabulary open, catalog = suggestion box.
- User's example [graph](graph data) already parses in the current grammar (first token = type, rest = attrs).
