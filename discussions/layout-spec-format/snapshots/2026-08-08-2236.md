# layout-spec-format — Snapshot

## Since last snapshot
Initial message. Starting position: user currently specs UI/UX with InterSpec (.is files, declarative UI language with state/events/navigation) + DESIGN.md (design tokens). User feels InterSpec is overkill for their workflow and proposes replacing it with a much simpler text format — LAYOUT.md / STRUCTURE.md or even LAYOUT.txt — where widgets are marked inline with markdown-link-style syntax: [label](button), [placeholder](input). They want opinion + suggestions, and know they need to define a simple, flexible format for interface structure.

## Active decisions
- None settled yet. Tentative lean: replace InterSpec at the structure layer; keep DESIGN.md for visual/tokens; adopt markdown-link-style inline widget markers ([label](type)).

## Open questions
- Filename/format: LAYOUT.md vs STRUCTURE.md vs LAYOUT.txt (value judgment)
- Exact marker syntax, and how to disambiguate from real markdown links (design tension — [Save](button) vs [Docs](https://...) are visually identical)
- Grammar scope: how to express nesting (card > title/input/buttons), repetition (grid of 5 cards), variants/states (primary, disabled) in linear text (design tension — the "flexible" requirement lives here; this is where simple formats bloat)
- Does the format need to express behavior (events, nav, conditionals) or pure static structure? (value judgment / design tension — behavioral scope is what makes it mini-InterSpec)
- Primary consumer: human-only communication artifact vs agent-consumed (implementation/verification) (value judgment — determines grammar budget)

## Reasoning chains
- InterSpec feels overkill because its real power is behavioral (state, events, navigation, reactivity) — if the user mostly writes "this screen has these things in this order," they pay for ~10% of the feature set. Structure-only spec doesn't need a programming language.
- Markdown-link syntax is a good seed: universal mental model, reads naturally, LLM-friendly.
- Insight: the inline widget marker is the easy part; nesting + repetition is the hard 10% where formats either die or bloat into mini-InterSpec.
- Insight: .txt variant escapes markdown-link collision but loses headings/lists/rendering; .md gives structure tools but collides with real links — prefix convention (e.g. [Save](@button)) is a cheaper fix than fleeing markdown.
- Precedent: Markdoc/MDX do "markdown + inline custom component markers" for content sites — validates the pattern, but nobody does it for app UI structure.

## Key insights
- Link-collision ambiguity is a bug in the seed idea, must be decided early (closed vocabulary vs prefix vs .txt).
- "Kind of flexible" is precisely the requirement that kills simplicity — needs an explicit scope decision.
