## Current state
## Active decisions (locked)
- LAYOUT.txt v1 grammar/verifier as exported; per-screen files; free-form vocabulary + minimal core (15 types).
- NEW (this turn, tentative): organization tiers — (1) static/template-driven sites: single LAYOUT.txt as the site shell; (2) multi-page apps: <page>.layout.txt flat; (3) feature-scale: folders with uniform LAYOUT.txt. Invariant: one file per distinct structure; filesystem is the index (no index/registry); glob = inventory (LAYOUT.txt / *.layout.txt / **/LAYOUT.txt).
- Distinctness rule: when a page within a template-driven site becomes genuinely distinct (e.g. contact page with form), split it into its own file — mixed usage is legal (LAYOUT.txt + contact.layout.txt side by side).

## Open questions

## Reasoning chains
- "Static vs app" is really "template-driven vs screen-driven": static sites' wireframe IS the template (content lives in the content layer); apps have genuinely distinct screens. User's instinct validated.
- Filename order mirrors label-first philosophy (screen name leads). LAYOUT.<page>.txt prefix vs <page>.layout.txt suffix: equivalent globs; suffix keeps the human-searched name first.
- One-file-one-screen invariant relaxed to one-file-per-distinct-structure for template-driven sites, with the split-off rule preserving per-page verification where it matters.

## Key insights
- Content-driven sites need per-page wireframes least — content IS the page data; the layout spec is the shell.
- Mixed organization (LAYOUT.txt + page.layout.txt) is legal and natural — no grammar change ever needed.
