## Since last snapshot
User answered questionnaire: (1) Consumer = BOTH — humans read, agents implement & verify. (2) Scope = "whatever makes sense to be present in a prototype/wireframe" — i.e. widgets, arrangement, hierarchy, labels, variants/states, annotations; NOT events/navigation/data logic. The verification requirement means the format must be deterministically parseable; the wireframe framing bounds the grammar.

## Current state
## Active decisions
- Replace InterSpec as the structure layer with a simple text wireframe format (tentative).
- Keep DESIGN.md for visuals/tokens (confirmed by user's setup).
- Markdown-link-style inline markers [label](type) as the seed syntax (tentative).
- Consumer: humans read + agents implement AND verify → format needs deterministic structure, not just prose.
- Scope: wireframe/prototype level — widgets, hierarchy, order, labels, variants/states, annotations. No behavioral programming semantics.

## Open questions
- Marker disambiguation from real markdown links: prefix (e.g. [Save](@button)) vs closed vocabulary vs .txt (design tension).
- Container/nesting mechanism for multi-widget groups: fence blocks, indented trees, inline brackets, or none (design tension — under discussion this turn).
- Repetition syntax (x3 / list items) (unexplored).
- Variant/state syntax: [label](type:variant), [label](type disabled) (unexplored).
- File naming: LAYOUT.md vs STRUCTURE.md vs LAYOUT.txt (value judgment; lean LAYOUT.md or WIREFRAME.md).
- Per-screen files vs one file (unexplored).
- How agents verify against LAYOUT.md (unexplored — candidate: marker types must exist in DESIGN.md components; DOM must match presence/order/hierarchy).

## Reasoning chains
- "Both consumers" + "wireframe scope" → grammar budget: needs parseable structure, variants, annotations; no state/events → stays far from InterSpec.
- Key new insight: LAYOUT.md needs to define NO vocabulary — widget types are referenced from DESIGN.md's components: section. [Save](button:primary) names a token that already exists. Verification falls out: unknown marker type = spec error; built DOM must match markers. This is what keeps the format tiny (a referencing layer, not a self-contained language).
- Key new insight: incompleteness as a feature — unlike InterSpec (a language where everything must be expressible), LAYOUT.md can have escape hatches ("if the format fights you, write a prose sentence"). Holes are OK because humans fill them; this is the real anti-bloat mechanism.
- Key new insight: same-line = row, new-line = column is a natural markdown-idiomatic ordering rule; markdown tables can express grids natively.
- Containers are unavoidable: multi-widget repetition (grid of cards) requires named groups.
